# 人机验证处理

只有上游明确返回 `decision.type=verify` 才作为人机验证。单独的 HTTP 429、限流或数字业务码不会触发客户端唤起。

## Windows 客户端版

从 v0.2.4 起，客户端版遇到 `verification_required` 时，恢复并置前已安装的豆包工作窗口。客户端未运行或已隐藏到托盘时，正常启动客户端以恢复窗口。独立登录浏览器和浏览器子进程不会被当作日常客户端。

1. 本次请求停止并返回验证错误，管理台提示需要验证的账号。
2. 在豆包工作对应账号中人工完成验证。
3. 在管理台点击“验证完成后探活”。探活成功后账号恢复可用，再重试原请求。

Windows 拒绝窗口置前时，恢复窗口并闪烁任务栏；点击任务栏中的豆包工作完成验证。客户端发现或唤起失败时，返回手动打开客户端的提示。多个并发提醒共用正在进行的唤起；之后再次收到验证要求时，会重新将窗口弹到前台。退出网关只结束自己的临时唤起程序，不关闭用户的豆包工作。

HTTP 拒绝、流式回复中的验证拒绝、模型和额度查询、账号检测、探活及客户端登录导入都支持提醒。提醒不携带 challenge、Cookie、验证码答案或原始错误体。完成验证后不会自动重发原对话；“探活”是用户主动发起的最小测试请求。

## 通用网关版与旧配置

通用网关版仍直接返回 `verification_required`，不自动唤起客户端。可在官网完成验证后主动探活，或在管理台添加账号以重新登录。

旧的 `DW_AUTO_CAPTCHA` 和 `DW_CAPTCHA_*` 启动配置保持停用。历史 `verification.mjs` 仍是停用的兼容接口。客户端版的新人工提醒独立于旧的自动识别和请求恢复功能，不加载本地验证码识别工具或模型。

两种版本都保留隐秘发送和回复后删除上游会话。验证失败、取消和超时后仍尝试清理本次已创建会话。

## 验证

- `npm test` 覆盖客户端限定、明确验证分类、HTTP/SSE、三种 API 协议、并发合并、唤起失败、关闭取消、账号探活恢复及不重发原请求。
- `npm run check:work-client`、`npm run check:admin` 检查新增入口和管理台语法。
- 将豆包工作切到后台或最小化，然后运行 `npm run smoke:work-client-verification`；加 `-- --sse` 可测试流式验证拒绝。本机测试通过临时网关模拟验证错误，不读取账号凭据或调用豆包 API。
